=====================================================================
GUIA DE INTEGRAÇÃO DO BACK-END COM O MODELO DE PREVISÃO DE ATRASOS
=====================================================================

0. RESUMO (UMA FRASE)
A API recebe dados brutos do voo, aplica exatamente as mesmas transformações
usadas no treino por meio do pipeline salvo, executa o modelo e retorna a
previsão de atraso e a probabilidade associada.


---------------------------------------------------------------------
1. CONTRATO DE ENTRADA (API)
---------------------------------------------------------------------
A API deve receber apenas dados conhecidos antes do voo.
O cliente NÃO precisa conhecer detalhes operacionais ou estatísticos.

Input (JSON):

{
  "icao_empresa": "TAM",
  "icao_aerodromo_origem": "SBGR",
  "icao_aerodromo_destino": "SBRJ",
  "partida_prevista": "2026-02-10T14:30:00",
  "tempo_voo_estimado_hr": 1.2,
  "distancia_km": 350
}

Output (JSON):

{
  "previsao_atraso": 1,
  "probabilidade": 0.89
}

Onde:
- previsao_atraso = 1 indica atraso (> 15 minutos)
- previsao_atraso = 0 indica voo no horário


---------------------------------------------------------------------
2. CARREGAMENTO DO MODELO (INICIALIZAÇÃO DA API)
---------------------------------------------------------------------
Na inicialização da API, deve ser carregado um único arquivo .joblib,
que contém:

- Pipeline completo de pré-processamento
- Target Encoding para variáveis categóricas
- Modelo XGBoost treinado
- Ordem final das features esperadas
- Threshold interno de decisão

Esse carregamento ocorre UMA ÚNICA VEZ no startup da aplicação.


---------------------------------------------------------------------
3. PRÉ-PROCESSAMENTO DO INPUT (OBRIGATÓRIO)
---------------------------------------------------------------------
Todas as transformações devem ser feitas ANTES da inferência, respeitando
exatamente a lógica usada no treino.


3.1 Derivação de features temporais
A partir do campo "partida_prevista", derivar:

- hora_prevista_frac
    Hora da partida em formato decimal
    Exemplo: 14:30 → 14.5

- mes
    Mês numérico (1 a 12)

- eh_fim_de_semana
    1 → sábado ou domingo
    0 → segunda a sexta-feira

- faixa_horaria
    Classificação da hora prevista:
      madrugada: 00:00–05:59
      manha:     06:00–11:59
      tarde:     12:00–17:59
      noite:     18:00–23:59


3.2 Variáveis operacionais internas (NÃO enviadas pelo cliente)

- voos_no_slot
    Quantidade de voos com partida prevista no mesmo aeroporto de origem
    e no mesmo intervalo de tempo (ex.: janela de 1 hora).

    Deve ser calculada internamente pelo back-end com base em dados
    operacionais, cache ou valor médio histórico por aeroporto.

- tempo_voo_estimado
    Utilizar o valor recebido em "tempo_voo_estimado_hr" (em horas),
    podendo aplicar ajustes internos se necessário.


3.3 Variáveis climáticas (extensão do modelo)

As seguintes variáveis são utilizadas como enriquecimento do modelo:

- temp        → temperatura média
- prcp        → precipitação
- wspd        → velocidade do vento
- prcp_bin    → indicador de chuva (0/1)
- vento_forte → indicador de vento forte (0/1)

Caso os dados climáticos não estejam disponíveis em tempo real:
- utilizar valores default documentados
- manter coerência com o pipeline salvo


3.4 Aplicação do Target Encoding
As variáveis categóricas são transformadas automaticamente pelo pipeline:

- icao_empresa
- icao_aerodromo_origem
- icao_aerodromo_destino
- faixa_horaria

Regras importantes:
- O pipeline já contém as estatísticas aprendidas no treino
- Categorias desconhecidas utilizam a média global
- NUNCA lançar erro por categoria nova


3.5 Montagem do vetor final de features
O back-end deve garantir que as features sejam fornecidas ao pipeline
com os nomes corretos e sem valores nulos.

A ordem final das features é gerenciada internamente pelo pipeline,
não sendo responsabilidade do back-end.


---------------------------------------------------------------------
4. FEATURES INTERNAS UTILIZADAS PELO MODELO
---------------------------------------------------------------------
Essas features são internas e NÃO devem ser expostas ao cliente:

- icao_empresa_aerea
- icao_aerodromo_origem
- icao_aerodromo_destino
- faixa_horaria
- hora_prevista_frac

---------------------------------------------------------------------
5. INFERÊNCIA
---------------------------------------------------------------------
Após o pré-processamento:

- predict()        → retorna classe final (0 ou 1)
- predict_proba()  → retorna probabilidade de atraso

A API deve retornar apenas:
- a previsão final
- a probabilidade estimada

O threshold utilizado é interno e pode ser ajustado sem alterar
o contrato da API ou retreinar o modelo.


---------------------------------------------------------------------
6. OBSERVAÇÕES FINAIS
---------------------------------------------------------------------
- O contrato mantém compatibilidade com a versão anterior do modelo
- As únicas extensões são distância e variáveis climáticas
- O cliente não precisa conhecer nenhuma feature interna
- O pipeline garante consistência entre treino e inferência

Este documento garante uma integração simples, segura e sem gargalos.
